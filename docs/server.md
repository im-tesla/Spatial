# Server setup

[← Spatial](../README.md)

Run the server on a machine with read access to the music files. The desktop connects through the server's HTTP API; the music does not need to be copied onto each client.

## Requirements

- A current stable Rust toolchain and the platform's native build tools.
- FFmpeg and FFprobe, available on PATH or configured with absolute paths.
- MediaInfo is recommended for explicit Atmos/JOC metadata detection when FFprobe cannot identify the profile.

Install these with the package manager appropriate to the host. The server is independent of the desktop's Tauri/WebView dependencies. Linux deployment helpers are included; the Rust server also runs on Windows for development. Other hosts have not been validated.

## Native Linux setup

Download or clone the repository, then run these commands from its root as a normal user:

```bash
cargo build --locked --release -p spatial-server
bash deploy/install.sh target/release/spatial-server
```

The installer creates `spatial.toml` with a random access token and preserves an existing configuration. Review that file before starting the service: choose the media directory, network bind address and executable paths. The template uses `/usr/bin/ffmpeg`, `/usr/bin/ffprobe` and `/usr/bin/mediainfo`; change these if the tools are installed elsewhere.

```bash
bash deploy/run-server.sh
```

The foreground launcher runs without service registration. Add `--log` to append output to `data/server.log`.

```text
project/
  spatial.toml           Configuration and access token
  bin/spatial-server     Server executable
  media/                 Default media directory
  data/library.sqlite    Catalog
  data/artwork/          Extracted artwork
  deploy/spatial.service Optional user-service unit
```

All generated Spatial files stay in the project. Relative media and data paths resolve against the directory containing the configuration file. The process runs under the existing user account, which needs read access to the media and write access to the data directory.

## Configuration

These are example settings; adapt the bind address and paths to the deployment:

```toml
bind = "0.0.0.0:8787"
media_dir = "media"
data_dir = "data"
api_token = "REPLACE_WITH_RANDOM_TOKEN"
ffprobe = "ffprobe"
ffmpeg = "ffmpeg"
mediainfo = "mediainfo"
rescan_seconds = 30
settle_ms = 1000
```

The placeholder token is rejected. Use the token generated by the Linux installer or provide a unique random token of at least 24 characters. `SPATIAL_API_TOKEN` overrides the configured token. Keep the configuration and token private; the example development token is for local development only.

To start a compiled server directly, pass a configuration path:

```bash
./target/release/spatial-server --config spatial.toml
```

On Windows, the corresponding executable is `target/release/spatial-server.exe`. The executable defaults to `spatial.toml` when no arguments are supplied.

## Connect a desktop client

Enter the address reachable from the client, including the scheme and any custom port. For example, a reverse-proxy deployment might use `https://spatial.example.com`; a direct connection uses the host's reachable address and configured port. The bind address `0.0.0.0` is not a client connection address.

The server provides HTTP. For access across untrusted networks, use an HTTPS reverse proxy or a private VPN. The desktop accepts HTTPS with valid certificates. Configure the firewall for the clients that need access.

Enter the same access token configured on the server. After a successful connection, the Windows app saves it in Credential Manager under `Spatial/ServerConnection`, for the current Windows account on that computer. Offline connections can be retried without re-entering the token. Use another token replaces a rejected token. Change server disconnects the session; the last successful connection remains remembered until another successful connection replaces it. Remove the Spatial entry from Windows Credential Manager to forget it entirely.

## Organize the library

Place tagged audio files in the configured media directory. Albums use album, album artist, artist, date, disc, track and release identifiers. Folder and filename conventions are optional. Missing tags use Unknown artist/album and the filename as the title; compilation tags support Various Artists.

Embedded artwork is preferred. Adjacent `cover.jpg`, `cover.png` or `folder.jpg` is a fallback. Source files are never rewritten or transcoded. Conflicting dates or release identifiers can split editions into separate albums; Spatial does not retag files or fetch replacement metadata.

The watcher indexes changes and sends catalog revisions to clients. A reconciliation scan also runs at the configured interval, covering filesystems where notifications are unavailable. For reliable imports, copy to an unsupported temporary extension such as `.part`, then rename to the final extension when complete. A paused copy can otherwise appear stable before it has finished.

## Optional systemd service

On hosts using systemd, register the generated unit with the user manager:

```bash
systemctl --user link "$(pwd)/deploy/spatial.service"
systemctl --user daemon-reload
systemctl --user enable --now spatial
systemctl --user status spatial
```

The unit stays in the project; registration creates the usual user-service links. User services normally follow the login session. If the project moves, rerun setup and update the service registration.

## Backups

Keep backups of the music and configuration. The media remains the source of truth, and the catalog can be rebuilt. Use SQLite's backup mechanism for a live catalog, or stop the server before copying its data directory. Copying only the main database file while WAL writes are active is not a complete backup.
